# Environment variables - every service in the RAG stack

How to configure the RAG platform end to end: which file each service reads, what every
variable does, which values must match across services, and what to create at the providers
(Google / Microsoft / Facebook OAuth, SMTP, LLM keys).

Rules used below:

- **Req** - `yes` = the service fails to start or a core feature breaks without it. `prod` = only required in production. `opt` = has a safe default or enables an optional feature.
- Never commit real values. Only `*.example` files are tracked; real files (`.env`, `.env.local`, `stacks/*/env/.env.*`) are gitignored.
- Generate secrets with `openssl rand -hex 32` (64 hex chars) unless a row says otherwise.

## 1. Map: who talks to whom

```
Browser --> Next.js frontend (:3000)
              |-- /api/auth/*  --> API gateway (:3301) --> IAM auth-service (:3304)
              |-- /api/iam/*   --> gateway (invites, connected accounts)
              `-- /api/rag/*   --> RAG API (:8088 local / :8000 in container)
                                     |-- IAM (JWKS + /auth/me)   [verifies every token]
                                     |-- Postgres+pgvector, Redis
                                     |-- file-upload-service (:4005)
                                     `-- LLM / embedding providers
IAM auth-service --> notification-service (:4004 on host)  --> SMTP (Mailpit locally, UI :8025)
                 --> Google / Microsoft / Facebook OAuth
```

| Service | Repo / location | Local env file | Example file |
|---|---|---|---|
| RAG API + worker | this repo | `.env` | `.env.example` |
| Frontend | `frontend/` | `frontend/.env.local` | `frontend/.env.local.example` |
| IAM auth-service | `Backend/multi-tannet-auth-services` | `easydev-infra/stacks/core/env/.env.auth` | `.env.auth.example` (and IAM repo `.env.example`) |
| API gateway | `Backend/web-agency-backend-api` | `stacks/core/env/.env.gateway` | `.env.gateway.example` |
| Shared core (Postgres/Redis/pgbouncer) | easydev-infra | `stacks/core/env/.env.shared`, `.env.postgres`, `.env.redis`, `.env.pgbouncer` | `*.example` |
| notification-service | `Backend/notification-service` | `stacks/utility/env/.env.app` | `.env.app.example` |
| file-upload-service | `Backend/file-upload-service` | `stacks/utility/env/.env.file-upload` | `.env.file-upload.example` |
| Production (all of the above) | easydev-infra | generated by `scripts/generate-env.sh` from GitHub Actions secrets | `scripts/secrets.example.env` |

## 2. Values that MUST match across services

If one of these is out of sync, the symptom is listed. This is the most common cause of "it worked on my machine".

| Value | Set in | Must equal | Symptom if wrong |
|---|---|---|---|
| Gateway public origin (`http://localhost:3301` locally) | IAM `CORS_ORIGINS`, provider OAuth redirect URIs, frontend `AUTH_GATEWAY_PUBLIC_URL` | each other | Social login fails with `Untrusted base URL override` or `redirect_uri_mismatch` |
| Frontend origin (`http://localhost:3000`) | IAM `FRONTEND_URL` + `CORS_ORIGINS`, gateway `FRONTEND_URL` + `CORS_ORIGINS`, RAG `CORS_ORIGINS` | each other | Blocked by CORS, or the post-login redirect goes to the wrong place |
| `IAM_INTROSPECTION_API_KEY` | IAM, RAG (`IAM_INTROSPECTION_API_KEY`) | same string | RAG cannot verify tokens: every request 401/503 with `AUTH_REQUIRED=true` |
| RAG `IAM_BASE_URL` | RAG | the **gateway** base (`http://host.docker.internal:3301` in Docker) | 401s / "Could not reach the IAM service" |
| RAG `IAM_JWKS_BASE_URL` | RAG | the **auth-service** base (`http://host.docker.internal:3304`) | Token signature cannot be verified |
| `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` | IAM only signs; public key copied to every verifier | the pair | All tokens rejected after a key change |
| `FILE_UPLOAD_HMAC_SECRET` | IAM, file-upload-service | same string | Signed upload/download URLs rejected |
| `GATEWAY_INTERNAL_SECRET` | gateway, file-upload-service | same string | Upload service refuses gateway calls |
| `NOTIFICATION_SERVICE_API_KEY` | IAM, notification-service (`API_KEY`) | same string | Invitation / verification emails never sent (401 from notification service) |
| `IAM_ADMIN_EMAIL` / `IAM_ADMIN_PASSWORD` | gateway | IAM `BOOTSTRAP_SERVICE_ACCOUNT_*` | Gateway cannot call IAM admin APIs |
| DB passwords | `.env.shared`/`.env.postgres` vs each service `DATABASE_URL` | each other | Service crash-loops on DB auth |
| `BACKUP_CODE_ENCRYPTION_KEY` | IAM only | exactly 64 hex chars, and **never rotated casually** | Every social sign-in and 2FA enrolment fails; rotating it makes already-stored provider tokens/2FA secrets unreadable |

Loaded by `docker compose` (`env_file: .env`) and by the local venv. Inside Docker, host names are compose service names (`postgres`, `redis`); the published host ports are Postgres `5442`, Redis `6389`, API `8088`.

### Authentication (IAM integration)

| Variable | Req | Local / example | Notes |
|---|---|---|---|
| **`AUTH_REQUIRED`** | prod | `false` in code; **`true` in local `.env`** | `true`: every route except health, docs, `/auth/refresh` needs a valid IAM bearer token (401 no/bad token, 503 IAM down); tenant/user come from the token, never from headers. `false`: legacy anonymous default-tenant behaviour. **Turn on in every real environment.** With it on, only the frontend (via `/api/rag`) sends tokens; curl / CLI / `/docs` "Try it out" get 401 |
| `ADMIN_ROLES` | opt | `super_admin,admin,tenant_admin` | Roles allowed to create agents, tool definitions, prompts (only enforced when `AUTH_REQUIRED=true`) |
| `IAM_BASE_URL` | yes | `http://host.docker.internal:3301` | The gateway, not the auth-service |
| `IAM_JWKS_BASE_URL` | yes | `http://host.docker.internal:3304` | The auth-service (publishes JWKS) |
| `IAM_INTROSPECTION_API_KEY` | yes | - | Must equal IAM's value |
| `IAM_CLIENT_ID`, `IAM_CLIENT_SECRET` | opt | empty | Only if the IAM client-credentials flow is used |
| `IAM_TIMEOUT`, `IAM_MAX_RETRIES`, `IAM_VERIFY_SSL` | opt | `30`, `3`, `true` | `IAM_VERIFY_SSL=false` only for local self-signed |

| `ENABLE_RBAC` | opt | `false` | Static default for the dynamic `enable_rbac` feature flag (permission-code checks on routes that use them) |

### Social login credentials

Enable per provider in IAM platform settings too: `auth.social.enabled` **and** `auth.social.<provider>` (`PUT /api/iam/settings/<key>` as super admin). Credentials come from env or from `auth.social.<provider>.client_id/.client_secret` (Facebook: `.app_id/.app_secret`) settings.

| Provider | Variables | Where to create |
|---|---|---|
| Google | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_CALLBACK_URL` | Google Cloud Console > APIs & Services > Credentials > OAuth client (Web) |
| Microsoft | `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT_ID` | Entra ID > App registrations |
| Facebook | `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET` | developers.facebook.com > Facebook Login |
| GitHub / LinkedIn / X / Apple | `IAM_GITHUB_*`, `LINKEDIN_*`, `TWITTER_*`, `APPLE_*` | Optional, not used by the frontend |

**Redirect URI to register at every provider** (scheme + host must be the gateway's public origin):

```
http://localhost:3301/api/auth/social/google/callback       (local)
http://localhost:3301/api/auth/social/microsoft/callback
http://localhost:3301/api/auth/social/facebook/callback
https://<DOMAIN_GATEWAY>/api/auth/social/<provider>/callback (production)
```

**Account-linking rules to know when testing**

- A social sign-in whose email matches an existing account is linked to it **only if the provider vouches for the email** (Google `email_verified`, Facebook confirmed email). Otherwise the user gets a 409 and must sign in with their password, then connect from **Settings > Connected accounts**.
- **Microsoft:** `MICROSOFT_TENANT_ID=common` (or `organizations`) is *not* trusted for email-based linking. Set a specific tenant id, or `consumers`, to allow it.
- A user with no password cannot disconnect their last provider.

## 10. Production (GitHub Actions secrets)

Production env files are **generated** on the VM by `scripts/generate-env.sh` from GitHub Actions secrets/variables forwarded by `.github/workflows/deploy-infra.yml`. The script fails the deploy with a message naming any missing required secret. The template of every name is `scripts/secrets.example.env`.

Deploy is manual: run the **deploy-infra** workflow after the images have been built by CI.

For the IAM social-login work, add:

| Name | Kind | Required | Value |
|---|---|---|---|
| `BACKUP_CODE_ENCRYPTION_KEY` | secret | **yes** | `openssl rand -hex 32` |
| `CORS_ORIGINS` | secret/var | recommended | Comma-separated frontend origins; the gateway and IAM origins are added automatically |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | secret | for Google | |
| `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET` | secret | for Facebook | |
| `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` | secret | for Microsoft | |
| `MICROSOFT_TENANT_ID` | secret/var | optional | Specific tenant id or `consumers` to allow email-based linking |

The RAG API and frontend are not part of this generator yet: they need their own production env (section 3 and 4) supplied wherever they are deployed, with **`AUTH_REQUIRED=true`**, `APP_ENV=production`, `DEBUG=false`, `LANGCHAIN_TRACING_V2=false` (unless keyed), real `IAM_*`, `UPLOAD_*`, LLM keys and HTTPS.

## 11. Order to fill things in, and how to check each step

1. **Shared core**: passwords in `.env.shared`/`.env.postgres`/`.env.redis`/`.env.pgbouncer`. Check: `docker ps` shows core-postgres/redis/pgbouncer healthy.
2. **IAM** (`.env.auth`): keys, secrets, `BACKUP_CODE_ENCRYPTION_KEY`, `CORS_ORIGINS`, bootstrap admin, notification URL/key. Check: `POST :3301/api/auth/login` with the bootstrap admin returns 200.
3. **notification-service** (`.env.app`): API key = IAM's, Mailpit or SMTP. Check: invite a user, see the email in Mailpit.
4. **file-upload-service**: secrets and storage. Check: upload a document from the UI.
5. **RAG** `.env`: LLM/embedding keys, `IAM_*`, `UPLOAD_*`, `AUTH_REQUIRED`. Check: `GET :8088/api/v1/health` = 200, and `GET /api/v1/knowledge-bases` without a token = 401.
6. **Frontend** `.env.local`: three URLs. Restart `npm run dev` after any change (env is read at start).
7. **OAuth providers**: create apps, register the redirect URIs from section 5, set credentials, then enable in IAM settings. Check: the login page shows the buttons; sign in with an email that already has a password account and confirm it links instead of creating a duplicate.

After changing any `.env`, recreate containers (`docker compose up -d`) - a plain restart does not always re-read `env_file`.
