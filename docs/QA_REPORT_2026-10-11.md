## 4. Findings

### F1 - Chat silently persists and displays a completely empty assistant reply, for at least some queries (High)

**Repro:** Admin, tenant EasyDev, fresh conversation. Message: *"What knowledge bases do you have
access to right now?"* → the UI shows a typing indicator for ~24 seconds, then renders an assistant
message bubble with **zero text** — just empty space and the thumbs-up/down feedback buttons, as if
a real reply had arrived. No error toast, no console error, no failed network request. The input
box re-enables normally, implying success.

**Confirmed via direct API read**, not just visual inspection —
`GET /api/v1/conversations/6428a8ca-eb96-4937-94b6-3b63403cf9de/messages` returns:
```json
{"id":"9545f735-...","role":"ASSISTANT","content":"","status":"COMPLETED","created_at":"2026-10-11T07:17:07.611826Z","sources":[]}
```
`status` is `COMPLETED`, not `FAILED` — the backend considers this a successful turn.

**Traced via the API container's logs** for `conversation_id=6428a8ca-...`:
```
{"node": "researcher", ..., "duration_ms": 16425.7, "event": "Graph node exited", ...}
{"node": "writer", ..., "event": "Graph node entered", ...}
{"node": "writer", ..., "duration_ms": 2422.29, "event": "Graph node exited", ...}
```
Both nodes exit cleanly, no exception logged anywhere. This points at a real multi-agent
"researcher → writer" subgraph (`packages/graph/nodes/researcher.py`,
`packages/graph/nodes/writer.py`) that doesn't appear in this repo's `docs/CHANGELOG.md` as of the
portion read this session — it decomposes a question into sub-questions, researches each in
parallel, then a `WriterNode` synthesizes one final answer. Two concrete spots worth checking first:
- `researcher.py:50` — `finding=result.get("finding", "")`: if a sub-question's research subgraph
  returns a dict with no `"finding"` key (e.g. it hit its own internal, silently-caught failure),
  this defaults to an **empty string with no error surfaced**, rather than failing the node or
  logging what went wrong.
- `writer.py:42-47` builds `synthesis_context` directly from those findings with no check for "are
  all findings actually empty" before asking the LLM to synthesize over them — if every finding is
  blank, nothing stops a correspondingly blank synthesis from being accepted and persisted as-is.

**Not universal — isolated by a second test.** A conversational message ("Say hello in one short
sentence") in a separate conversation worked correctly: real text, ~10s round trip, no bug. This
message almost certainly skipped the research subgraph; the first one's phrasing clearly reads as a
request for retrieved/factual information, so the planner likely routed it into the broken
researcher→writer path. **This means any question a user phrases as an information request, not
obvious small talk, risks this failure mode** — a serious finding for a RAG platform whose entire
purpose is answering exactly that kind of question.

**Impact:** the user sees what looks like a successful, confident response that says nothing — no
"I don't know," no error, no indication anything went wrong. That is worse than an error for trust
in the product, and it would look the same across every role, not just Admin.

**Screenshots:** `C:\Users\kisho\AppData\Local\Temp\claude-chrome-screenshots-zpT183\screenshot-1791703221943-1.jpg`
(the empty reply), contrasted with the working reply earlier in the same session.

## 5. Performance observations

All 22 non-Chat routes loaded in a tight, healthy band:

| Metric | Range |
|---|---|
| `responseStart` (TTFB) | 360ms - 1.14s |
| `domContentLoadedEventEnd` | 680ms - 1.23s |
| `loadEventEnd` | 630ms - 1.4s |

No route was a standout outlier in either direction except two on the slower end of the band —
**Analytics** (1.29s) and **Usage** (1.38s) — both still well under 1.5s and not concerning on their
own, but both are the two pages whose `/api/` payload (30-day aggregates) is the heaviest of the
set, which is a plausible, non-alarming explanation.

**Chat is the real outlier, and not from page load** — the page itself renders instantly. The two
real data points are:
- A simple conversational message: ~10s end-to-end (acceptable for an LLM round trip, no retrieval).
- A question that triggers the researcher→writer subgraph: **~24 seconds**, dominated by the
  `researcher` node's single 16.4-second span (parallel sub-question research) plus the `writer`
  node's 2.4 seconds — and in this case, that 24 seconds produced nothing visible. Even setting F1
  aside, 24 seconds for one chat turn is a real latency concern worth measuring across more queries
  before calling it normal multi-agent overhead versus something slower than intended (e.g. the
  sub-question research subgraphs running close to serially rather than fully parallel, or an
  avoidable retry/backoff somewhere in that 16.4 seconds).

No other page made a slow or failing `/api/` call; every one of the ~140 API requests observed
across the full route sweep returned 200 except the one expected `405` (`GET /conversations` isn't
a real endpoint — the test script's own mistake, not a product bug: the real route needs a
conversation id).

## 6. What needs to happen to fix F1

1. Reproduce directly against `packages/graph/nodes/researcher.py` / `research.py` subgraph with a
   unit/integration test using the exact failing query, to see what each sub-question's research
   subgraph actually returns — confirm whether `finding` really comes back empty, or whether the bug
   is downstream in `writer.py`'s prompt construction or `normalize_message_content`.
2. Wherever the true empty-content point is, it should **raise or log a visible warning**, not
   silently produce a `COMPLETED` message with empty content — at minimum, fail the turn or fall back
   to a plain non-research answer rather than showing the user nothing.
3. Once fixed, re-run this same repro query live to confirm a real, non-empty answer, and check a
   few more fact-seeking phrasings to make sure this isn't narrower or wider than this one query.
4. Separately, profile the researcher node's 16.4s — confirm the sub-question subgraphs really run
   concurrently (`asyncio.gather`, as the code intends) rather than effectively serially.
